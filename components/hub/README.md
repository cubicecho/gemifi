# hub

The base component of every **hub**: a chip or circuit that gives pins (shift registers, multiplexers, I/O expanders, matrices, LED strips and drivers). Every device builds it (`REQUIRED = True`). `gm_hub.h` (the driver interface and the per-hub state, and at its end what the base gives a driver), `__init__.py` (`HubType`, the class every hub type's builder part derives from, and the builder parts several types share: `ShiftRegister`, `I2CExpander`, `rgb_curve`, `validate_rgb_calibration`). The pins a hub gives, and how the YAML names them: [core/README.md "Pins"](../../core/README.md#pins).

## Hub drivers

Each hub type is a driver behind one interface, `gm_hub_ops_t` (`gm_hub.h`), listed in `hub_ops[]` (`core/src/vpin.c`) by type. The driver is in the type's component, `components/<key>/` (its ops come in through the generated `gm_components.h`). `gm_hub_t` is the hub's type and that type's own config, a union member generated by the builder (`.sr`, `.mux`, `.mx`, ...: `core/include/gm_device.h`, or the component's header); each hub's state (`gm_hub_state_t`) is a few common fields (`in`, `out`, `written`, `channel`, ...) and a union of each type's own. The ops, all optional:

| Op | Called by | Runs |
|---|---|---|
| `init` | `vpin_init` | start-up: control pins to their idle levels, state to power-up |
| `input`, `output` | `vpin_input`, `vpin_output` | start-up: a pin is read / driven (I2C: direction and pull-up bits) |
| `read`, `write` | `vpin_read`, `vpin_write` | anywhere. Without them: the cached `in` / `out` words |
| `analog` | `vpin_analog` | the main loop: 0..4095 on a channel (mux, XY pad) |
| `rgb` | `vpin_rgb` | a whole colour on an LED (LED strips); a hub with it is full-colour: its LEDs take full-colour looks ([Full-colour LEDs](../../core/README.md#full-colour-leds)) |
| `refresh`, `flush` | `vpin_refresh` / `vpin_flush` in the scan tick (HC165 / HC595), or with `GM_HUBF_BUS` `vpin_refresh_i2c` / `vpin_flush_i2c` from the main loop (I2C) | inputs into `in`; `out` to the chip if it changed |
| `send` | `vpin_poll` every main-loop pass, and `vpin_send_all` | what changed on a bit-banged chip (TM1628, MAX7219, TM1637), at most a budget of bus bytes a pass (4, ~50 µs on the STM32); none on a busy pass (the LED update's) |
| `poll` | `vpin_poll` every main-loop pass | protocol timing (maudio_pads: one LED per 5 ms, the keepalive, acks; ws2812: a frame when something changed) |

`flags` say what else the core needs to know: `GM_HUBF_IN_REG` (`in` holds the pins' levels, so a key scan can read a column with one load), `GM_HUBF_NO_READ` (outputs only), `GM_HUBF_BUS`, `GM_HUBF_SELECT` (decoder outputs: "off" does nothing), `GM_HUBF_MATRIX`. The controller asks `vpin_caps()` / `vpin_pin_caps(pin)` (`VPIN_SCAN_IO`, `VPIN_BUS_IO`, `VPIN_MAIN`, `VPIN_MATRIX`, `VPIN_RGB`) which loops to run and what a pin can do, instead of looking at hub types.

The scan's hot paths don't go through the table: `vpin_read` on a mux channel and on a cached input, `vpin_write` on a decoder row and on a cached output, and the switch-matrix scan (`vpin_scan_matrices`, the hardware scan's `vpin_scan_plan` / `vpin_scan_feed`) are written out in `vpin.c`, so a pin costs what it did before the table. So the mux, decoder, switch matrix, TM1628 and XY pad keep the config or state the core reads in `gm_device.h` / `gm_hub.h`. Hub types with more than pins keep their own calls in `gm_vpin.h`: the TM1628's `fade:`, the mux's hardware analog scan, the XY pad's `vpin_analog_jump`.

The builder writes `GM_HUB_TYPES` (a bit per hub type the device has) into `gm_device_config.h`; `hub_ops[]` holds only those drivers, and only the components the device uses are compiled (the Keystation, with no hubs, links none).

## Adding a hub type

A component of its own ([core/README.md "Adding a component"](../../core/README.md#adding-a-component)). One of several chips for one job is a platform of a base component instead: [Adding a strip platform](../led_strip/README.md#adding-a-strip-platform), [Adding a driver platform](../led_driver/README.md#adding-a-driver-platform).

1. **`components/<key>/`**, a folder named after the YAML key (types that share a driver share one, as `cd74hc4051` and `cd74hc4067` do in `cd74hc4067/`), as [ws2812](../ws2812/) is: `<key>.c` (its ops and a `const gm_hub_ops_t gm_<key>_ops`), `<key>.h` (its config struct and, if it keeps any, its state struct, which the generated `gm_components.h` adds to `gm_hub_t`'s and `gm_hub_state_t`'s unions; `vpin_init` resets the state before `init`), `__init__.py`, `README.md` and `test/`. The end of `gm_hub.h` lists what the base gives a driver: pins kept in the hub RAM (more than 32 of them, or bytes per pin) take `gm_hub_ram_alloc(n)` bytes there in `init` (count them into `GM_HUB_RAM` with `ram = True`); control pins are set up with `gm_hub_mcu_out`; I2C chips use `gm_hub_i2c_*` and their bus ([i2c](../i2c/README.md)).
2. **`core/include/gm_device.h`**: a `GM_HUB_*` value (before `GM_HUB_N_TYPES`). A config bigger than the largest (the decoder's, 36 bytes) makes every hub bigger: point at a `const` table instead (as the switch matrix's rows and the LED hubs' `curve` do).
3. **`__init__.py`**: a `HubType` subclass (its YAML key, `enum` and `num`, its `keys`, the control pins' `lines`, `roles`, `validate`, `c_fields` for its union member, `c_tables` for anything the entry points at, and `c_header`, `c_config`, `c_state`, `c_ops` for its C), listed in `HUB_TYPES`. A hub with an `rgb` op sets `full_colour = True` (and `colour_pins` if an LED isn't 3 pins): its LEDs then take full-colour looks, `led_defaults` and step colours as they are. Old keys of a type go in `old_keys`, refused with the new form (`moved_text`). What it needs of the builder is `components/api.py` (the pin model: `Pin`, `NO_PIN`, the pin flags), the validator its calls get (`v`: `v.pin`, `v.err`, ...) and the platform (`v.plat`); it doesn't import `gemifi_device`. The YAML key, the pin key, the schema and the "which hubs can be an input / output / analog" checks follow from it. Then `gemifi_build.py schema -o site/src/schema/device.json`.
4. **Tests**: a core test YAML with the hub and its test in `test/` (run by `core/test`), and a builder test of its validation and C.
